# Фронтенд: канвас на React Flow (`@canvas/web`)

Редактор с нодами «текст → генератор → результат», сохранением через REST и имитацией генерации изображения. React 19, TypeScript, `@xyflow/react` 12, Vite. Бэкенд не менялся.

[Задание](../../docs/ASSIGNMENT.md) · [API](../../docs/INTEGRATION.md) · [Критерии оценки](../../docs/EVALUATION.md)

## Запуск и сборка

Потребуются Node.js 24.x и npm 11.x. Из корня репозитория:

```sh
npm ci             # установка всех зависимостей (включая фронтенд)
npm run dev        # API на http://localhost:4001
npm run dev:web    # фронтенд на http://localhost:5173 (второй терминал)
```

Сборка и проверки (из корня, фронтенд включён):

```sh
npm run build      # contracts + api + web
npm run test       # тесты API и модульные тесты фронтенда
npm run check      # форматирование, сборка, тесты, OpenAPI
```

Те же команды работают и внутри `apps/web`: `npm run dev`, `npm run build` (tsc + vite), `npm run test`, `npm run preview` для собранного приложения.

Дальше: откроется экран пространств → «Создать и открыть» → канвас. После перезагрузки страницы открывается то же пространство (id хранится в `localStorage`). Swagger API: [http://localhost:4001/docs/](http://localhost:4001/docs/).

## Структура

```text
src/
  api.ts                 общий клиент: fetch, статусы, разбор, ошибки; описания запросов
  graph.ts               конвертация «сервер ↔ React Flow», правила связей, сравнение снимков
  saveQueue.ts           очередь сохранений: debounce, один PUT, конфликт 412, потерянный ответ
  generationTracker.ts   запуск и опрос генераций, идемпотентность, восстановление
  Canvas.tsx             экран канваса: состояние графа, обработчики, статусы сохранения
  nodes.tsx              три типа нод и контекст действий
  App.tsx                список пространств, создание, открытие по перезагрузке
test/                    модульные тесты очереди сохранений и правил графа
e2e/smoke.mjs            браузерный сценарий (опционально, см. ниже)
```

## Устройство работы с API

Все запросы проходят через одну функцию `request()` в `src/api.ts`:

- адрес API и общие заголовки (`Content-Type`, `If-Match`, `Idempotency-Key`) ставятся в одном месте; особенность запроса — только метод, путь и форма тела;
- статус, пустое тело и разбор JSON проверяются общим кодом; `ETag` и `Retry-After` читаются там же;
- сетевая ошибка, HTTP-ошибка и ошибка разбора приводятся к одному виду `ApiError(status, code, message)`. Компоненты и очереди получают готовые данные или `ApiError` и отвечают только за отображение — повторных `response.ok`/`response.json()` нет нигде;
- стартовые загрузки собраны в `loadWorkspace()`: пространство, граф с ETag, генерации и `/api/config` — одним `Promise.all`.

Служебные поля React Flow (`selected`, `dragging`, `measured`, обработчики) не сохраняются: `toGraph()` собирает из состояния только поля схемы (id, type, position, data), `fromGraph()` разворачивает серверный граф обратно. Правила связей «текст → генератор → результат», один вход, один выход генератора — одна функция `canConnect()`; она же используется и как `isValidConnection` при перетаскивании, и в `onConnect`.

## Debounce и очередь сохранений

Очередь — класс `SaveQueue` без привязки к React (`src/saveQueue.ts`), покрыт модульными тестами.

- **Debounce 500 мс.** Любое изменение вызывает `markDirty()`, который перезапускает таймер. Серия быстрых правок даёт один PUT после паузы; правка во время выполняющегося запроса делает «грязным» снова.
- **Последовательность.** Одновременно выполняется не более одного PUT: отправки выстраиваются в цепочку промисов, а внутренний цикл `while (dirty)` после завершения запроса сразу отправляет свежий снимок, если правки накопились. Снимок сериализуется **в момент отправки**, поэтому медленный ответ не может затереть более новое состояние — UI живёт на своих ссылках и от ответов PUT не зависит.
- **ETag.** Очередь хранит актуальный ETag из ответов GET/PUT и передаёт его в `If-Match`. Кнопка «Сгенерировать» сначала вызывает `flush()` (отменяет таймер и дожидается фактического сохранения) и запускает генерацию только при `idle` — сбой сохранения запуск не допускает.
- **412.** Локальные правки остаются на экране, очередь переходит в `conflict` и не рвётся к серверу; в шапке появляется объяснение и кнопка «Загрузить серверную версию» — явная замена локального черновика серверным графом (`reset()` с новым ETag).
- **Потерянный ответ (сбой сети на PUT).** Запрос мог успеть выполниться, поэтому очередь перечитывает граф и сравнивает с отправленным снимком (`sameGraph`): совпало — принимается серверный ETag без повторной записи; не совпало — те же байты отправляются повторно с актуальным ETag. Старый запрос не повторяется вслепую.
- **Что не сохраняется.** Выделение нод и промежуточные события перетаскивания: сохранение запускают только изменения позиции (по завершении перетаскивания), состава и содержимого.

## Генерации

`GenerationTracker` (`src/generationTracker.ts`) — тоже отдельный от React класс: один на страницу, а не по копии на ноду.

- запуск: `POST` с новым `Idempotency-Key` (UUID) и `graphETag` из очереди сохранений; неполная цепочка проверяется локально и не отправляет запрос;
- опрос: статус читается по `Location` с паузой из `Retry-After` (далее — `pollIntervalMs` из `/api/config`); опрос останавливается на конечном статусе, при закрытии пространства и на размонтировании (`dispose()`);
- результат пишется по сохранённому `resultNodeId`: изменение графа во время генерации не может подставить картинку в другую ноду, а завершение старой попытки не затирает более новую запись;
- повтор: после сетевой ошибки запуска — с тем же ключом (запрос мог дойти), после серверного `failed` — с новым ключом;
- восстановление после перезагрузки: список генераций идёт от новых к старым, берётся первая запись по каждой ноде генератора; `processing` продолжает опрашиваться, результат появляется у связанной ноды результата.

## Разбор горячего участка

Самый частый участок — ввод текста в ноде. Нажатие клавиши проходит путь `setText → commit → снимок при сохранении`:

1. `setText` делает **один проход** `map` по нодам: новый массив + новый объект только у редактируемой ноды, остальные N−1 объектов сохраняют ссылки. Промежуточных массивов нет; дырок в массиве нет (никаких `delete arr[i]` — только `filter`, дающий плотный массив).
2. Сериализации на нажатие нет: `JSON.stringify(toGraph(...))` вызывается только в момент фактического PUT (не чаще одного раза в 500 мс), а не на каждое изменение. `toGraph` — один проход по нодам и один по связям без промежуточных коллекций.
3. React Flow мемоизирует ноды по ссылке объекта, поэтому рендерится только изменённая нода; остальной канвас не пересчитывается. Контекст действий стабилен (`useCallback`/`useMemo`), тики опроса генераций обновляют небольшие map'ы (≤20 записей), а `resultFor` строится одним проходом по значениям.
4. Валидация связей (`isValidConnection`) срабатывает на каждое наведение при перетаскивании связи. Чтобы не искать тип ноды линейным проходом каждый раз, `typeIndex` — `Map` из `id → тип`, построенный **одним проходом на изменение состава нод**, а не на каждое обращение; проверка самого соединения — O(1) по индексу плюс O(рёбра) на занятость порта (рёбер ≤ 20).

## Проверенные сценарии

Автоматически — `npm run test`: серия правок даёт одно сохранение; правка во время запроса уходит следующим PUT с ETag из ответа; 412 останавливается в конфликт без повторов и снимается `reset`; потерянный ответ распознаётся перечитыванием (совпал — принять ETag, не совпал — повторить с актуальным); `flush` без правок ничего не отправляет; правила связей и кругосветка `fromGraph → toGraph`.

Браузерный сценарий `e2e/smoke.mjs` (опционально; не входит в `npm test`): нужен `playwright-core` и любой Chromium/Chrome, запущенные API (:4001) и dev-сервер (:5173):

```sh
npm i -D playwright-core
CHROMIUM=/путь/к/chrome node e2e/smoke.mjs
```

Проверено вручную и этим сценарием: создание пространства и открытие после перезагрузки; добавление, перемещение, редактирование и удаление трёх типов нод; связи перетаскиванием, запрет несовместимых и дублирующих, удаление ноды вместе со связями; статус сохранения в шапке; центровка портов нод по вертикали; генерация с ожиданием и картинкой в ноде результата; тестовый отказ с повтором; восстановление графа, текста, позиции и результата после перезагрузки; на сервере — только поля схемы, без `selected`/`measured`; ошибок в консоли нет.

## Настройки

Адрес API по умолчанию — `http://localhost:4001`; фронтенд работает на любом localhost-порту (CORS API это разрешает). Сменить адрес API фронтенда: `VITE_API_BASE=http://localhost:4101 npm run dev` (из этой папки или `npm run dev:web` из корня).

Генерация тестовая: после задержки сервер возвращает локальное SVG-изображение или ошибку сценария. Сброс данных API — `npm run data:reset` из корня при остановленном сервере.
